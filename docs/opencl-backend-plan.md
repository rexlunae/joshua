# OpenCL accelerator backend for joshua (design + plan)

**Status:** M1 hardware proof done. **Owner:** joshua (this repo). **Target:** run the
DeepSeek-V4-Flash benchmark on an Intel OpenCL GPU (iGPU now; M40 via the
NVIDIA OpenCL ICD when reconnected) through a joshua-native `--device opencl`.

## 0. Why this is a big project (set expectations)

joshua's accelerator path is `candle_core::Device`, which has **no trait-based
pluggable backend** — it is an **enum** with concrete variants:

```rust
pub enum Device { Cpu, Cuda(CudaDevice), Metal(MetalDevice) }
pub enum DeviceLocation { Cpu, Cuda{..}, Metal{..} }
```

and a parallel `Storage` enum (`CpuStorage/CudaStorage/MetalStorage`), a
`backend` trait method on storage, and per-`Location` operator dispatch
(matmul, index_select, scatter, gather, narrow/cat, to_dtype, …). There is
**no OpenCL anywhere** in candle-core 0.11.0 (verified: only `cpu`, `cuda`,
`metal`).

So "add an OpenCL path" = add a **new device+storage+location+operator-lowering
backend** to the vendored candle-core (we already `[patch]` candle crates, so
patching was sanctioned) **and** teach joshua's GGUF loaders to target it. That
is the same shape as the CUDA/Metal backends — i.e. a **multi-day, kernel-heavy
effort**, not a flag.

The OpenCL driver side is ready on the host:
`intel-opencl-icd` installed → `Intel(R) OpenCL Graphics` / `UHD Graphics 730`
enumerates; `intel.icd` + `nvidia.icd` both present. OpenCL headers + `-lOpenCL`
resolve.

## 1. Interface surface the backend must implement

From `candle-core-0.11.0/src/`:

- `Device` enum gains `OpenCl(OpenClDevice)`; `DeviceLocation` gains `OpenCl`.
- `Storage` enum gains `OpenClStorage` (analogous to `CudaStorage`, holding a
  device buffer + shape+dtype).
- `backend` trait method: `to_cpu_storage()` and friends implemented for
  `OpenClStorage` (read-back for the CPU/fallback path and for `to_vec1`).
- Operator dispatch under `OpenCl` for **at least**: `zeros`, `from_vec`,
  `matmul` (f32; later quant), `index_select`, `scatter`, `gather`,
  `arg_sort_last_dim`, `narrow`/`cat`, `to_dtype`, elementwise (`affine`,
  `sqr`, `sum_keepdim`, …), `index_add` (used by MoE `dispatch`).
- `Device` constructors: `new_opencl(ordinal)`, `opencl_if_available`.
- joshua `device.rs`/`main.rs` `DeviceArg` gains `opencl`.

(Full op inventory to be generated by `cargo run -- dump_ops` style trace —
see §4.)

## 2. Two candidate architectures

**A. Patch `candle-core` vendored `Device` enum (+ Storage + backend + ops).**
Most faithful; reuses all of joshua's `candle` calls unchanged. Cost: touch
many files in the vendored crate; risk of churn against upstream candle diffs.

**B. An OpenCL "shim device" that exposes a `Cpu`-compatible storage in RAM and
executes kernels out-of-band.**
Far less invasive (no candle-core enum patch), but loses transparent
`Storage` semantics — every op would need special-casing; likely slower and
more code overall for deepseek4. **Recommend A** (the same way CUDA/Metal are
real backends).

## 3. Kernel inventory for DeepSeek-V4-Flash on OpenCL

The hybrid design keeps **dense on device, experts on CPU**, so the OpenCL
backend only needs the **dense** ops at first (attention, norms, routers,
shared experts, output):

- f32 GEMM (int8/f16-quant later) — attention & gating
- RMSNorm / elementwise affine
- softmax + `sum_keepdim` (attention scores / sink)
- index_select / gather (token-embd, routing)
- RoPE / Hadamard (head_dim) — f32
- `hc_pre`/`hc_post` (hc_mult=4 mix/sum) — elementwise + weighted sum
- indexer / compressor small matmuls
- final `output`/`token_embd` matmul

Experts stay CPU (72.5 GiB → do NOT push to the iGPU's ~57 GiB shared mem /
weak dGPU). So OpenCL first covers the **dense** path; the expert mmap load is
CPU as today.

## 4. Test / validation plan

1. Minimal OpenCL backend compiles against Intel ICD; unit test: zeros, from_vec,
   matmul equal a known CPU result (bit-level where exact).
2. `--device opencl` runs `run` on the tiny deepseek4 GGUF (dense via OpenCL,
   experts CPU), matches CPU/CUDA logits within f32 sum-order tolerance.
3. JOSHUA_PROFILE_LAYERS on the real DS4-Flash `--device opencl` → same
   correctness + a real iGPU throughput number for the dense set.
4. When M40 reconnects: add an `opencl` GPU-vs-CUDA cross-check on the same op.

## 5. Milestones (each independently mergeable + testable)

- **M0.** Scoping doc (this file). ✅
- **M1.** `candle-core`: add `OpenCl` location+device+storage skeletons; `zeros`
  + `from_vec` + `to_cpu_storage` round-trip; unit test. (Reaches the GPU: a
  tensor can live on OpenCL and come back.)
  - **M1 hardware proof ✅ (2026-09-13):** `docs/ocl_roundtrip.c` verified PASS on
    `Intel(R) UHD Graphics 730` — host→device→host f32 buffer round-trip
    (`clEnqueueWriteBuffer`/`clEnqueueReadBuffer`), the raw equivalent of
    `OpenClStorage::from_vec`/`to_cpu_storage`. Combined with the earlier
    `docs/ocl_smoke.c` kernel-exec PASS, the data path + kernel path are both
    proven on the iGPU. Remaining: wire `OpenClDevice`/`OpenClStorage` into the
    vendored `Device`/`Storage`/`DeviceLocation` enums behind the `opencl`
    feature (the coupled storage.rs/device.rs/backend.rs change), then the in-
    crate round-trip unit test.
  - **M1 wiring ✅ (commit `11fcf68`):** `opencl_backend/mod.rs`
    (`OpenClDevice`/`OpenClStorage` + hand-rolled libOpenCL FFI) and
    `dummy_opencl_backend.rs` (no-feature dummy) wired into the
    `Device`/`Storage`/`DeviceLocation` enums; joshua `opencl` feature added
    (`candle-core/opencl`). `cargo check` (no-feature) and
    `cargo check --features opencl` both green on the dev Mac. Round-trip
    verified by `tests/opencl_roundtrip.rs` (feature-gated) — run it on the
    host iGPU via `cargo test --features opencl --test opencl_roundtrip`.
- **M2.** Elementwise + `matmul` (f32) + `index_select`/`gather`/`narrow/cat`
  on OpenCl; unit vs CPU.
- **M3.** joshua `--device opencl` + `DeviceArg::opencl`; tiny-model parity test.
- **M4.** Dense deepseek4 over OpenCL on the real model; `JOSHUA_PROFILE_LAYERS`
  benchmark = the deliverable "same benchmark on OpenCL" numbers.
- **M5.** (optional) quantized dense kernels; M40-OpenCL cross-check.

Each milestone lands as its own PR. M1–M4 are the "run the benchmark" critical
path.
