# candle-core MXFP4 upstream contribution

This directory is a **standalone mirror of `candle-core` 0.11.0** (vendored
from crates.io, commit `e416d9f`) with a new feature implemented on top:

## `GgmlDType::Mxfp4` — Microscaling FP4 (GGML_TYPE_MXFP4 = 39)

DeepSeek-family GGUF files (e.g. DeepSeek-V4, DeepSeek-R1 "QK2" repacks)
ship tensors with GGUF dtype 39 (MXFP4). Upstream candle-core 0.11.0 has no
such dtype: `GgmlDType::from_u32(39)` bails, so those models cannot be
loaded. This branch adds MXFP4 as a first-class dtype.

Format (OCP MX spec): a block of 32 elements = one E8M0 exponent byte + 16
bytes of packed 4-bit E2M1 codes → **17 bytes / 32 elements (4.25 b/e)**.
Codes use the doubled kvalues table
`[0,1,2,3,4,6,8,12,0,-1,-2,-3,-4,-6,-8,-12]` with scale `2^(e-128)`.

### What was added

- `src/quantized/k_quants.rs`: `BlockMxfp4` (`#[repr(C)]`, size-checked to
  17 bytes) with a `GgmlType` impl ported verbatim from llama.cpp:
  - `from_float` = `quantize_row_mxfp4_ref` (ggml-quants.c)
  - `to_float` = `dequantize_row_mxfp4` (ggml-quants.c)
  - `vec_dot` = `ggml_vec_dot_mxfp4_q8_0_generic` (ggml-cpu/quants.c);
    `VecDotType = BlockQ8_0` matches llama.cpp's pairing of MXFP4 weights
    with Q8_0-quantized activations.
- `src/quantized/mod.rs`: `GgmlDType::Mxfp4` wired through `from_u32`/`to_u32`
  (id 39), `cpu_zeros`, `from_data`, `type_size` (17), `block_size` (32), and
  `QStorage::from_data` (CPU/Metal/CUDA load paths).
- `src/quantized/ggml_file.rs`: load MXFP4 tensors from legacy GGML files.
- `src/quantized/metal.rs`: MXFP4 dequantize arm; the `From<GgmlDType>` for
  `candle_metal_kernels::GgmlDType` became a `TryFrom` that errors clearly —
  the kernels crate has no MXFP4 kernels, so this is **CPU-only** (CUDA
  already bails cleanly on unsupported dtypes).
- `tests/mxfp4_tests.rs`: golden bytes generated by compiling llama.cpp's
  reference quantizer as standalone C (bit-exact pinning), an independent
  reference decode, a GGUF write/read round trip, and dtype plumbing.
- `tests/quantized_tests.rs`: MXFP4 in the generic quantized-matmul and
  CPU-embedding coverage. Matmul tolerance relaxed to 0.15 (E2M1's 2-bit
  mantissa carries far more quantization error than any other candle dtype).

### Validation

- `cargo test` — full suite green (default features, x86_64).
- `cargo clippy --all-targets` — clean (one pre-existing vendored warning in
  `src/shape.rs`).
- `cargo fmt --check` — clean.
- Bit-exactness vs llama.cpp proven by the golden tests, which were produced
  by the *actual* llama.cpp reference implementation compiled to a C binary.

### Notes for the upstream PR

- **Opened: https://github.com/huggingface/candle/pull/3899** (branch
  `rexlunae:mxfp4-core`, two commits, applied on current `main`). Cross-
  linked to the pre-existing open PR **#3391** ("Mxfp4 gpt oss
  implementation", infosechoudini, open since March 2026, zero reviews),
  which adds Metal/CUDA kernels + the gpt-oss model on top of an
  equivalent core dtype implementation. Our PR is the smaller core layer
  (dtype plumbing + bit-exactness tests); the two compose.
- Metal/CUDA matmul support intentionally out of scope: candle-metal-kernels
  and candle-kernels have no MXFP4 kernels; `TryFrom`/existing `_` arms give
  explicit errors rather than silent miscompute.
- The `GgmlDType::Mxfp4` name follows candle's `BF16` casing; llama.cpp calls
  it `GGML_TYPE_MXFP4`; #3391 uses `MXFP4`. Cosmetic, reconcile on review.
